# Проверка перед публичной публикацией

Дата: 28 октября 2026 года. Среда: Windows, Python 3.12.14. Проверка выполнена с помощью Codex, независимого обзора кода и автоматических инструментов. Это не внешний сертифицированный аудит и не гарантия отсутствия всех возможных уязвимостей.

## Объект и границы

Проверены `app.py`, `storage.py`, `time_utils.py`, HTML-шаблоны, CSS/JavaScript, зависимости, тесты и состав файлов для Git. Приложение рассчитано на локальный запуск на `127.0.0.1` с вымышленными данными. Авторизация и интернет-развёртывание не входят в объём задания. Публикация исходников на GitHub не размещает работающий сервер в интернете.

Исходные 49 тестов повторно прошли перед изменениями. При добавлении защиты Host новые тесты выявили ошибку обработчика HTTP-ошибок; она исправлена. Финальный набор дополнен сценариями постороннего Host с отсутствующим CSRF и чрезмерным телом запроса.

Известные уязвимости пакетов проверялись по актуальным ответам PyPI на указанную дату. Для уже закреплённых полных зависимостей использовались `--no-deps --disable-pip`; файлы пакетов при аудите повторно не устанавливались. Инструменты аудита установлены в отдельное игнорируемое окружение и не добавлены в зависимости приложения.

## Найдено и исправлено

1. **Произвольный Host.** Ранее тестовый клиент мог получить страницу и выполнить POST под посторонним Host. Для локального приложения это создаёт предпосылку DNS rebinding, с оговоркой о дополнительных ограничениях браузера. Разрешены только `localhost` и `127.0.0.1`; проверка выполняется до разбора формы. Поддельный `X-Forwarded-Host` не учитывается.
2. **Ошибка при отклонении Host.** Flask ещё не создаёт URL-адаптер при ошибке Host, а шаблон ошибки использовал `url_for()`. Регрессионные тесты воспроизвели исключение. Для этого случая возвращается короткий текстовый ответ 400. Проверяется также сочетание постороннего Host с отсутствующим CSRF или слишком большим телом.
3. **Гонка первого создания секрета.** Второй процесс мог прочитать пустой файл до окончания записи первого. Полный ключ теперь атомарно публикуется через жёсткую ссылку; чужой уже созданный ключ не перезаписывается. Файл временного ключа удаляется после публикации. Неправильный существующий ключ останавливает запуск с объяснением.

Критических уязвимостей в проверенном коде и известных уязвимостей закреплённых зависимостей на момент проверки не обнаружено. Это вывод в указанных границах, а не обещание абсолютной безопасности.

## Что проверялось дополнительно

- Серверная валидация имени, описания, пустых значений, нулевых символов и неверных ID.
- Параметризованные SQL-запросы; пользовательские строки не становятся SQL-кодом.
- Экранирование пользовательского HTML и атрибутов в Jinja, отсутствие `innerHTML` и выполнения пользовательского кода в JavaScript.
- POST для изменений, CSRF-токен, запрет изменений через GET, лимит тела запроса.
- Заголовки CSP, запрет фреймов, HttpOnly и SameSite=Lax для cookie.
- Отказы при попытках обхода пути статических файлов; слишком длинные числовые ID и повреждённые session cookies не приводят к необработанной ошибке в проведённых пробах.
- Единственный активный таймер на сотрудника на уровне SQLite; одновременные HTTP-старты и остановки.
- Сохранение после перезапуска, календарные границы и полночь, точное суммирование до форматирования, пустые результаты, согласованный снимок отчёта.

Предыдущая проверка браузера включала создание вымышленных сотрудников, таймер, перезагрузку страницы, настоящий перезапуск процесса, отчёты и ширины 375/1280. После исправлений безопасности повторно выполнены серверные тесты; отдельная новая браузерная сессия не проводилась.

## Состав публикации

В репозиторий входят исходники, шаблоны и стили, закреплённые зависимости, тесты, README, учебный разбор, этот отчёт, `.gitignore` и `.gitattributes`. Проверены все 17 текстовых файлов непосредственно из индекса Git: UTF-8, отсутствие содержимого базы, локального секрета, шаблонов токенов/закрытых ключей и путей профиля пользователя. `git diff --cached --check` прошёл; окончания строк нормализованы. Локальная база, секрет сессии, виртуальные окружения, временные файлы, снимки проверки и локальные заметки исключены.

## Оставшиеся ограничения

- Приложение без учётных записей не предназначено для открытого сервера с реальными данными сотрудников. CSRF и Host-проверка не заменяют авторизацию.
- Для локального HTTP не включены Secure-cookie и HSTS. Публичное развёртывание требует отдельной настройки HTTPS, WSGI-сервера, доступа и резервного копирования.
- Нет пагинации и ограничений частоты запросов: это небольшой локальный проект. Проверка не включала нагрузочное тестирование и внешний сетевой пентест.
- Системные часы и диск должны работать корректно. После сна компьютера на некоторых платформах нужно обновить страницу для синхронизации видимого счётчика.
- Первое создание локального секрета требует файловой системы с жёсткими ссылками; альтернативно можно задать `TIMEKEEPER_SECRET_KEY` извне.

Для повторения тестов используйте команды из README. Для независимого сканирования можно установить Bandit и pip-audit в отдельное окружение и выполнить:

```text
python -m bandit app.py storage.py time_utils.py
python -m pip_audit --disable-pip --no-deps --strict -r requirements.txt
```

Основания для решений: [проверка Host и безопасность Flask](https://flask.palletsprojects.com/en/stable/web-security/), [документация pip-audit](https://pypi.org/project/pip-audit/).
