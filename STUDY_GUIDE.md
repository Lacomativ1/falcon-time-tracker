# Как устроено приложение «Рабочее время»

Этот файл помогает разобраться в решении и подготовиться к собеседованию. Читать код и запускать приложение лучше одновременно: сначала повторить действие в браузере, затем найти соответствующий обработчик в `app.py`.

Код и документация подготовлены с помощью ИИ в Codex. Это не означает, что кандидат уже самостоятельно написал, проверил или понял каждую строку. На собеседовании стоит честно разделять помощь инструмента и то, что вы уже можете объяснить и изменить сами.

## 1. Общая картина

В приложении есть три основные части:

1. Браузер показывает страницу и отправляет формы.
2. Сервер на Python проверяет данные, запускает и останавливает задачи, строит отчёт.
3. SQLite сохраняет сотрудников и временные отметки в файле на диске.

Сервер не увеличивает счётчик каждую секунду. Он сохраняет момент начала, а при остановке — момент окончания. Если между ними прошло десять минут, длительность равна разности этих отметок. Поэтому для активной задачи не нужен отдельный постоянно работающий процесс.

## 2. Что здесь делают технологии

| Технология | Роль в приложении |
| --- | --- |
| Python | Выполняет серверную логику: проверки, работу с датами и расчёт отчёта. |
| Flask | Связывает адреса и HTTP-запросы с функциями Python, принимает формы и возвращает страницы. |
| SQLite | Хранит таблицы в одном файле; отдельный сервер базы данных не нужен. |
| HTML и Jinja | Описывают страницу. Jinja подставляет сотрудников, задачи и результаты отчёта в HTML. |
| CSS | Задаёт цвета, размеры, расположение блоков и поведение на узком экране. |
| JavaScript | Обновляет видимый счётчик активной задачи. Сохранением рабочего времени он не управляет. |
| pytest | Запускает автоматические сценарии и сравнивает результат с ожидаемым. |

При отключённом JavaScript формы продолжают отправляться серверу. Чтобы увидеть новое значение счётчика, нужно обновить страницу.

## 4. Как запрос попадает в Python

Когда вы открываете главную страницу, браузер отправляет `GET /`. Flask вызывает обработчик главной страницы, тот читает базу и передаёт данные в `index.html`. Браузер получает уже сформированную страницу.

Когда вы нажимаете «Начать», форма отправляет `POST /timers/start`. Сервер читает поля, проверяет их, сохраняет задачу и возвращает перенаправление с кодом 303. Браузер снова открывает главную через GET и показывает сообщение.

Такой порядок полезен при обновлении страницы: обычное обновление повторяет просмотр, а не создание записи. Защита от двух почти одновременных POST всё равно нужна отдельно — её обеспечивает база.

GET используется для просмотра и фильтрации. Создание сотрудника, запуск и остановка меняют данные, поэтому выполняются через POST.

## 5. Как сохраняется сотрудник

Форма отправляет поле `name` в `POST /employees`.

Сервер убирает пробелы по краям и проверяет, что имя не пустое и не длиннее 100 символов. Затем выполняет параметризованный SQL-запрос: текст имени передаётся отдельным значением, а не вставляется в SQL как команда.

SQLite создаёт строку в таблице `employees` и назначает ей числовой `id`. Два сотрудника могут называться одинаково, но их ID будут разными. Задачи привязаны именно к ID.

Пример состояния таблицы:

| id | name |
| --- | --- |
| 1 | Алексей Тестов |
| 2 | Марина Примерова |

Запись остаётся на диске после завершения транзакции. Перезапуск Python сам по себе её не удаляет.

## 6. Что происходит при запуске таймера

1. Браузер отправляет ID сотрудника, описание и CSRF-токен.
2. Сервер проверяет токен и существование сотрудника.
3. Описание очищается от крайних пробелов; пустой текст и текст длиннее 1000 символов отклоняются.
4. Сервер получает текущее время от своего источника времени.
5. В `time_entries` добавляется запись с `started_at`; `ended_at` пока равен `NULL`.

`NULL` здесь означает «время окончания ещё не задано», а не нулевую дату.

Временные отметки хранятся целыми микросекундами от начала Unix-эпохи в UTC. Это позволяет считать разности и суммы без ошибок дробных чисел. Длительность не хранится отдельной колонкой: её можно получить из начала и окончания.

## 7. Почему нельзя запустить второй таймер тому же сотруднику

У SQLite есть частичный уникальный индекс: для строк, у которых `ended_at IS NULL`, значение `employee_id` должно быть уникальным.

Это значит, что у сотрудника может быть много завершённых задач, но только одна активная. Если два запроса попытаются создать активную задачу одновременно, база сохранит одну и отклонит другую. Сервер обработает отказ и покажет понятное сообщение.

Проверка только в JavaScript или отключённая кнопка не дали бы такой гарантии: пользователь может открыть две вкладки или отправить запрос напрямую.

Повторный запуск не обновляет исходную запись и не сбрасывает её `started_at`. Разные сотрудники могут иметь активные задачи одновременно.

## 8. Остановка и повторная остановка

Кнопка отправляет `POST /timers/<id>/stop`, где `<id>` — ID записи рабочего времени.

Сервер фиксирует текущее время в `ended_at` только у активной записи. Условие обновления проверяет, что окончание ещё не задано. Повторная остановка не переписывает сохранённое значение.

Если системные часы неожиданно ушли назад, окончание ограничивается временем начала. Так длительность не становится отрицательной. Дополнительно это правило защищено ограничением базы данных.

После остановки запись перестаёт попадать под уникальный индекс активных задач. Сотрудник снова может начать новую задачу.

Несуществующий сотрудник или ID задачи обрабатывается как ошибка 404. Это не должно превращаться в необработанное исключение на странице пользователя.

## 9. Откуда берётся счётчик после обновления страницы

Начало задачи уже записано в SQLite. При каждом открытии страницы сервер вычисляет:

```text
прошедшее время = максимум(0, текущее время сервера − сохранённое начало)
```

JavaScript получает начало и текущее серверное время со страницей. Затем он добавляет время, прошедшее после загрузки, и меняет только видимый текст счётчика. Часы компьютера посетителя не определяют сохранённую длительность.

После обновления страницы расчёт начинается заново от сохранённой отметки. После перезапуска сервера происходит то же самое. Пока сервер выключен, активная задача продолжает считаться: в модели приложения она не была остановлена.

## 10. Как строится отчёт

В отчёт входят завершённые записи. Активные задачи показаны отдельно и попадут в итог после остановки.

Пользователь задаёт первую и последнюю календарные даты и, при необходимости, сотрудника. Обе даты включаются целиком. Внутри программы период задаётся так:

```text
[полночь первой даты, полночь дня после последней даты)
```

Левая граница включена, правая исключена. Поэтому задача, которая закончилась ровно в начале выбранного дня, не добавляет в него времени.

Для каждой подходящей записи берётся только пересечение с периодом:

```text
начало пересечения = максимум(начало задачи, начало периода)
конец пересечения = минимум(конец задачи, конец периода)
длительность = максимум(0, конец пересечения − начало пересечения)
```

Пример в зоне Asia/Dushanbe: задача началась в 23:50 и закончилась в 00:20. Отчёт за первый день покажет 10 минут, за второй — 20 минут. Отчёт за оба дня покажет 30 минут, а не всю задачу в каждом дне.

Сервер суммирует микросекунды по сотрудникам и только затем форматирует итог. Две записи по 0,6 секунды дают 1,2 секунды, то есть на экране итог `00:00:01`; преждевременное округление каждой записи потеряло бы эту секунду.

При форматировании дробная часть секунды отбрасывается. Часы не сбрасываются после 24: например, 25 часов, 1 минута и 1 секунда отображаются как `25:01:01`.

Сотрудник без записей получает нулевой итог. При пустом периоде страница показывает сообщение об отсутствии записей. При обратном диапазоне дат показывается ошибка фильтра, а отчёт не рассчитывается.

## 11. Зачем UTC и Asia/Dushanbe

UTC — единая временная шкала для сохранения моментов. Календарный день зависит от зоны: полночь в Душанбе наступает раньше полуночи UTC.

Поэтому приложение сохраняет отметки в UTC, а даты фильтра и подписи переводит через явно заданную зону Asia/Dushanbe. Зона видна в интерфейсе. Вычислять границы отчёта по часовому поясу браузера было бы неоднозначно: у двух посетителей мог бы получиться разный «сегодняшний день».

Тест с задачей через местную полночь помогает заметить ошибку, которую проверка обычной дневной задачи не обнаружила бы.

## 12. Что защищает данные

- Сервер повторно проверяет поля: атрибуты HTML `required` и `maxlength` помогают пользователю, но не заменяют проверку Python.
- SQL-параметры отделяют данные от SQL-команд.
- Jinja экранирует пользовательский текст: введённый HTML отображается как текст.
- CSRF-токен связывает отправленную форму с сессией браузера. Без верного токена изменяющий запрос отклоняется.
- Разрешены только Host `localhost` и `127.0.0.1`. Это мешает чужому домену обращаться к локальному приложению через DNS rebinding. Посторонний Host отклоняется до разбора формы.
- Секрет сессии публикуется только после полной записи, без перезаписи ключа другого процесса. Повреждённый ключ останавливает запуск вместо создания неработающей сессии.
- Ограничения SQLite защищают от двух активных таймеров, отрицательного интервала и ссылки на несуществующего сотрудника.
- Локальная база, секрет, виртуальное окружение и кэши исключены из будущего репозитория.

CSRF не является авторизацией. В приложении нет учётных записей и разграничения доступа. Оно предназначено для локальной демонстрации на вымышленных данных.

## 13. Как читать и запускать тесты

Сначала прочитайте фикстуры в `tests/conftest.py`: это заготовки, которые pytest создаёт перед проверкой. Каждая проверка получает временную базу. Объект `Clock` позволяет тесту переставить серверное время, например, сразу на час вперёд.

Тест «запустили задачу — прошёл час — остановили» не ждёт час. Он задаёт нужные отметки времени и проверяет сохранённый результат.

Для запуска из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Для одного сценария:

```powershell
.\.venv\Scripts\python.exe -m pytest -q -k crossing_local_midnight
```

Среди проверок есть обычные действия пользователя, повторные запросы, пустой отчёт, перезапуск, границы периода, CSRF, экранирование и одновременные записи в базу. Тест ограничения SQLite проверяет поведение базы отдельно от кнопки браузера.

Количество и фактический результат выполненных проверок смотрите в README. Наличие тестового файла само по себе ещё не означает, что тесты запускались или прошли успешно.

## 14. Как искать причину ошибки

1. Запишите точные шаги, выбранные даты и сообщение. Используйте вымышленные данные.
2. Установите, где проблема: внешний вид, ответ сервера или расчёт/сохранение.
3. Найдите адрес формы в `index.html`, затем соответствующий обработчик в `app.py`.
4. Для ошибок расчёта проверьте исходные временные отметки, зону и границы периода. Для ошибки сохранения — условия SQL и ограничения таблицы.
5. Посмотрите вывод терминала сервера. Не публикуйте секреты и содержимое локальной базы.
6. Добавьте короткий тест, который воспроизводит проблему. Исправьте причину и снова запустите этот тест и весь набор.

Если проверка падает, полезны три значения: что ожидалось, что получилось и при каких входных данных. Не стоит менять ожидаемое значение только ради зелёного результата: сначала нужно решить, какое поведение верно по ТЗ.

Фактически найденные при разработке проблемы описаны в разделе README «Ошибки и исправления». Ограничение или предотвращённый риск не следует выдавать за обнаруженный баг.

## 15. Три примера небольших изменений

Эти инструкции объясняют путь изменения. Сами дополнительные возможности здесь не внедряются.

### Изменить подпись кнопки

Откройте `templates/index.html`, найдите текст `Начать` внутри кнопки формы таймера и замените, например, на `Начать задачу`. Не меняйте `action` формы и имена полей. Обновите страницу и проверьте отправку формы.

Если меняете подпись кнопки остановки, проверьте также её `aria-label`: это подпись для вспомогательных средств доступности.

### Добавить сотруднику поле «Отдел»

Изменение проходит через все слои: поле HTML → чтение и проверка в Python → колонка SQLite → вывод в шаблоне → тесты.

Одного изменения команды создания таблицы недостаточно: существующая база уже создана. Нужна небольшая миграция, например добавление необязательной колонки `department` с пустым значением по умолчанию. Её следует выполнять один раз с проверкой текущей схемы; повторный запуск приложения не должен снова добавлять ту же колонку.

Перед изменением рабочей базы сделайте её копию при остановленном сервере. Затем проверьте и свежую базу, и обновление существующей: прежние сотрудники и записи должны сохраниться. Новому полю задайте разумное ограничение длины. SQL-параметры и экранирование нужны и для него.

### Изменить период отчёта

Чтобы изменить период по умолчанию с сегодняшнего дня на последние семь дней, найдите обработку отсутствующих `start_date` и `end_date` в главном обработчике. Конечная дата остаётся сегодняшней в зоне приложения, начальная — на шесть дней раньше. Шесть, потому что обе границы календарных дат включаются.

Явно выбранные пользователем даты должны иметь приоритет. Не меняйте правило полуоткрытого интервала и пересечения задач. Добавьте проверку, что без параметров выбираются семь календарных дней, а с параметрами сохраняется выбор пользователя.

## 16. Вероятные вопросы на собеседовании

### 1. Почему выбран такой стек?

Flask позволяет выразить небольшой набор адресов обычными функциями Python. HTML-шаблоны не требуют отдельной сборки интерфейса. SQLite хранит данные без отдельного сервера. Для этого объёма задачи стек остаётся небольшим и доступным для разбора.

### 2. Почему SQLite, а не серверная база?

Для локального тестового задания достаточно одного файла и транзакций. SQLite поддерживает нужные внешние ключи и уникальный индекс. При большом количестве одновременных записей и размещении на нескольких серверах стоило бы рассмотреть PostgreSQL и пересмотреть развёртывание.

### 3. Почему таймер нельзя хранить только в JavaScript?

Вкладку можно закрыть или обновить; клиентскому времени нельзя доверять. Здесь в базе хранится серверная отметка начала, а JavaScript только показывает разность. Сохранённый результат определяет сервер.

### 4. Что будет при двойном нажатии «Начать»?

База разрешит только одну активную запись для сотрудника. Второй запрос получит понятное сообщение, а время начала первой задачи останется прежним. Это работает и при запросах из разных вкладок.

### 5. Что будет при повторной остановке?

Сохранённое окончание не переписывается: запрос обновляет только запись без `ended_at`. Повтор не добавляет длительность.

### 6. Что произойдёт при перезапуске сервера?

Сотрудники, завершённые задачи и активное начало остаются в SQLite. После запуска приложение читает тот же файл. Активный счётчик продолжится от сохранённого начала, включая время, пока сервер был выключен.

### 7. Как учитывается задача через полночь?

Каждый отчёт берёт пересечение задачи с календарным периодом в Asia/Dushanbe. Для задачи 23:50–00:20 первый день получит 10 минут, второй — 20 минут.

### 8. Почему активные задачи не входят в итог?

Это выбранное и явно указанное правило отчёта: итог строится по завершённым записям. У активной задачи ещё нет окончательного времени окончания. Она видна отдельным блоком и попадёт в отчёт после остановки.

### 9. Как устроен пустой отчёт?

Отсутствие записей — обычный результат, а не исключение. Общий итог равен нулю, у выбранного сотрудника также показан ноль, страница объясняет, что за период записей нет.

### 10. Зачем точность до микросекунд, если экран показывает секунды?

Чтобы не терять дробные части при суммировании. Форматирование выполняется после расчёта суммы. Для хранения используются целые числа, а не числа с плавающей точкой.

### 11. Как проверялся код, созданный ИИ?

Можно показать реальные тесты и фактический отчёт проверок из README: серверные сценарии с управляемым временем, ограничения базы, границы дат и проверку интерфейса, если она выполнена. Не следует говорить «я проверил», пока вы сами не повторили запуск и не изучили результат.

### 12. Какие ошибки были найдены?

Назовите конкретную проблему из README: как она проявилась, почему возникла, что изменено и какой проверкой подтверждено исправление. Нельзя придумывать историю или называть заранее добавленную защиту найденной ошибкой.

### 13. Зачем CSRF, если нет авторизации?

Приложение всё равно принимает изменяющие формы из браузера. Токен мешает посторонней странице незаметно отправить форму от имени открытой сессии. При этом он не ограничивает доступ пользователей к данным и не заменяет авторизацию.

### 14. Какие ограничения есть у решения?

Это локальная демонстрация без учётных записей, прав доступа и редактирования записей. Работа с реальными сотрудниками через открытый интернет потребует дополнительных решений. Правило одной активной задачи относится к сотруднику, а не к браузеру.

### 15. Что изменить для нескольких пользователей и как честно объяснить ИИ?

Для независимых пользователей нужны вход, принадлежность данных организации, проверка доступа на сервере и подходящее развёртывание. Если люди будут одновременно работать с одной общей командой, нужно сначала уточнить правила доступа и конфликтов.

Про ИИ можно сказать: «Для подготовки кода, интерфейса, тестов и документации использовался Codex. Я могу показать запросы и результаты проверок. Сейчас я разбираю решение и могу объяснить такие-то части». Последнюю фразу следует дополнить только тем, что вы действительно уже понимаете и можете продемонстрировать.

## 17. Практика перед собеседованием

Попробуйте самостоятельно три изменения из раздела 15, по одному за раз:

1. Переименуйте кнопку «Начать» в «Начать задачу» и проверьте действие в браузере.
2. Добавьте необязательный «Отдел» с сохранением в базе; проверьте существующую и новую базу.
3. Сделайте последние семь дней периодом по умолчанию и добавьте проверку явного выбора дат.

Перед каждым изменением сохраните рабочую копию. После изменения запустите тесты и объясните своими словами, какие файлы пришлось изменить и почему. Если второй пункт пока сложен, сначала разберите путь поля `name` от HTML до SQL и обратно.
